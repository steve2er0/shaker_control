Shaker Control: controls and interface audit

Audit of commit 3aa27a97079e829889849822bec03df82a6fb415, performed on 2026-10-14. Application source was not modified. Findings combine code review, native Qt screen captures, and simulation-only control/state probes.

Main recommendation: align the interface with one authoritative run state and one validated configuration per run. Then organize the interface around a persistent run bar, a mode-specific primary plot, compact setup controls, and a results review.

Confirmed mismatches

  • An accepted 1,000 Hz sampling rate failed initialization while the UI remained “Running”; Start stayed disabled and Stop did not recover the screen. The worker's status signal had no GUI receivers.
  • Applying an 8,000 Hz sample rate left the data viewer using 51,200 Hz.
  • The configuration form's Apply button was at y = 1,172 in a 729-pixel viewport at a 1,200 × 800 window size, requiring scrolling.
  • Random initial level 5.0 and sine initial level 2.0 are accepted by widgets, despite control bounds of 2.0 and 1.0 respectively.
  • A packet with no target PSD left the previous random target curve on screen. An ordinary metrics refresh removed the EQ bars; the next EQ update added another legend entry.
  • The monitor accepted a 10-second PSD window but retained only 2 seconds of samples. A fault message was overwritten with “Stopped.”

Recommended flow

Set up → Validate → Ready → Start → Run → Stop/Complete → Review. A fault is a separate retained state. Backend, test mode, effective target, logging status, and Stop remain visible across all views.

  • Run workspace: make Run the main screen, place settings in a compact panel, and keep advanced tuning behind a disclosure. This follows the owner's earlier preference for a large viewport and compact tools.
  • Guided setup: offer a setup-first path with validation and an effective-configuration review before starting. Useful for unfamiliar hardware or test profiles.
  • Random: response and target PSD are primary; g RMS, ramp percentage, and AO clipping have separate units and readouts. EQ is a diagnostic view with a band-derived frequency range.
  • Sine: measured and target g-peak versus frequency are primary; show current frequency, initial settling, sweep progress, and drive-table provenance. Hide random-only PI and EQ controls.
  • Monitor: acceleration and PSD are primary; show effective window length, resolution, configured channels, and acquisition backend. No drive controls.

Implementation order and acceptance

  1. State and configuration: connect structured worker status, completion, and faults to the GUI; clean up threads on every exit; distinguish requested versus actual backend; capture immutable validated settings for each run. A failed start must display Fault, restore a usable start path, and retain the reason. An unexpected hardware-to-simulation transition must be visible and explicit.
  2. Control consistency: validate Nyquist and block/PSD/buffer relationships; align widget limits with effective limits; show peak/RMS and amplitude/PSD distinctions; keep Stop visible in every view. Applying settings must either rebuild affected views before the next run or mark them as draft changes.
  3. Screen structure and plotting: add the persistent run bar, make setup compact and mode-specific, reset curves and histories per run, prevent stale targets and duplicate legends, split metrics by quantity, and use consistent colors and elapsed-time axes. Random-to-sine-to-random switching must never show a previous target or stale mode's diagnostics.
  4. Run review: retain effective backend, settings, channels, units, calibration source, limits, and log paths with each run. Surface results and fault history in the application.

Evidence screens

These are captures of the existing native Qt widgets using the offscreen platform, not images of the proposed interface. The random and sine views contain actual simulation packets. The failure screenshot comes from a real initialization failure before DAQ setup.

Proposal checks

The local browser preview passed checks for invalid sample-rate feedback, apply/start/stop state transitions, persistent Stop during review, mode-specific plots and units, removal of irrelevant monitor controls, and the guided setup flow. Layouts were checked at 320 and 1,024 pixels with no horizontal overflow. Browser console errors: none.

Validation boundaries

  • Native Qt widgets were captured with the offscreen platform; macOS chrome, keyboard/screen-reader usability, and physical DAQ behavior were not validated.
  • Simulation packets were supplied through the existing worker and UI methods; this is a workflow audit, not a sustained performance or hardware tracking test.
  • No production application code was changed; artifacts are local and uncommitted.

The proposed interface is an interactive design sketch with illustrative data. It does not execute the application, open hardware tasks, or record a real run. The existing native GUI and the proposal were evaluated separately.
